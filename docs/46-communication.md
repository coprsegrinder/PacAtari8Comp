# 46 - Communication (stage 68)

GENERATED by `python -I tools/comm_map.py --write analysis/evidence-comm-summary.txt` and `python -I tools/analyze_comm.py --doc docs/46-communication.md` from the static read / write sets of the contexts of the game (`tools/absint6502.py`, the names of `25`), their check on the concrete 6502 and the curated text of `tools/analyze_comm.py`; tests: `tests/test_comm.py`. What crosses the boundary of the machine is `45`; this chapter is the other half of the question: **the game does not communicate with anything outside the machine, and inside it the parts that run interleaved talk through a short, listed set of variables.**

## 1. The result

- **No communication with the outside, of any kind** (`45`, section 5): no file, device, serial-bus, modem or network access (no `CIO`, no `SIO`, no page 3, no serial data register, no PIA) and two OS calls (`SETVBV`, `XITVBV`). The cartridge is the only code; nothing is received but the 14 declared inputs. Stage 68 is a *measured* "nothing", not an assumption. **There is no multiplayer link either**: the second player is the same machine, taking turns (section 5).
- **Inside the program there are 5 contexts on one CPU** (section 2): the key loop, the new-game sequence it starts, the vertical-blank handler (the whole game frame) and the two display-list handlers. They share **103 zero-page variables and 10 memory regions** (section 3); **12** of those variables are a hand-over between the key loop or a display-list handler and another context (section 4); the rest is the new game's clears and initialisations, which the frame handler then reads.
- **The static sets were run, not only read** (section 6): 1000 runs of the contexts from random states on the concrete 6502; every cell below `$4000` read or written (outside the stack, the ROM and the accesses through a pointer, which `42` classifies) lies in the static set of its context: **0 outside**.
- **For a port**: the display-list handlers only *read* what the frame handler and the key loop leave (5 and 2 variables) and touch the chips; in a port they are a per-band table of colours and character-set pages (`35`, section 4), with no communication to keep. The key loop is an **event poll** that writes 11 variables and regions (section 4: `GameState`, `Paused`, `TwoPlayers`, `StartLevel`, the countdown and attract-mode variables, `IntroRequest`, `KeyDebounce`, `DliColors`). The frame handler is **one function call per frame** (`44`). A port that runs the poll and the frame in turn, between frames, carries the whole of the original's communication in section 4. The original interleaves them at any instruction; that this is harmless is the original's protocol (section 5), not something this stage proves (section 7).

## 2. The contexts

| Context | Entry | Runs | Can be interrupted by | Instructions (with callees) | Reads | Writes |
|---|---|---|---|---|---|---|
| main program: the key loop | `$A4BA` | all the time the interrupts leave free, never returns | the vertical-blank handler (at any instruction) and the display-list handlers | 87 | 12 | 11 |
| main program: the new-game sequence it starts | `$A477` | once per game: entered from the key loop (`$A541`, START), back to it (`$A4B6`) | the same: it runs in the main program's time, between interrupts | 231 | 10 | 105 |
| vertical-blank handler (the frame) | `$A5FD` (`VVBLKD`) | once per frame (60 / s NTSC) | the display-list handlers (non-maskable); it does not interrupt itself (it ends within the frame, `38`) | 2577 | 110 | 114 |
| display-list interrupt, game screen | `$A573` (`VDSLST`) | five times per game frame, at the band lines (`35`) | nothing (an NMI is not interrupted by an NMI) | 44 | 5 | 3 |
| display-list interrupt, title | `$A5CE` (`VDSLST`) | five times per title frame | nothing | 25 | 2 | 3 |

`Reads` / `Writes` count zero-page variables (the names of `25`; an indexed access counts its whole variable) and the memory regions of `42` that the context and every routine it calls can touch (accesses through a pointer are in `29` and `42`). The key loop and the new-game sequence are one thread of control (the key loop jumps to the sequence and the sequence jumps back); the frame handler and the two display-list handlers are the interrupts.

## 3. What is shared

Variables and regions that one context writes and another reads or writes. The number written by the row and read by the column:

```
row/col       key newgame     vbi    dli1    dli2
key             -       3       8       1       1
newgame         4       -      97       1       0
vbi             7       5       -       2       1
dli1            1       0       1       -       1
dli2            1       0       1       1       -
```

The large number in the `newgame` row is the **initialisation of a game and of a board**: the new-game sequence clears `$20-$3F` and the sound chip itself and calls `InitBoard`, which clears `$80-$FF` and loads `$80-$93` (`43`, section 4); the frame handler reads every game variable afterwards. It is a hand-over of the whole state, in one direction, before the first frame of the game acts on it (section 5).

Shared memory regions (not zero page): `Antic` (written by dli1/dli2/newgame/vbi, read by none), `Gtia` (written by dli1/dli2/newgame/vbi, read by key/vbi), `MazeScreen` (written by newgame/vbi, read by newgame/vbi), `OsPage2` (written by key/newgame/vbi, read by key/vbi), `PmMissiles` (written by newgame/vbi, read by none), `PmPlayers` (written by newgame/vbi, read by none), `Pokey` (written by newgame/vbi, read by vbi), `SavedMaze1` (written by newgame/vbi, read by vbi), `SavedMaze2` (written by newgame/vbi, read by vbi), `StatusRows` (written by newgame/vbi, read by vbi).

## 4. The hand-over variables

The variables the key loop or a display-list handler shares with another context (the new game's bulk initialisation left out):

| Variable | Address | Written by | Read by | What it is |
|---|---|---|---|---|
| `ATRACT` | `$4D` | key, vbi | - | the OS attract-mode counter (the game clears it on a key and at the countdown) |
| `BandCounter` | `$18` | dli1, dli2, vbi | dli1, dli2 | display-list band number: cleared by the VBI, +1 at every DLI; selects the colours and CHBASE of the band |
| `CountdownActive` | `$20` | key, newgame, vbi | key, vbi | 1 while the game-over countdown runs; cleared by a new game |
| `CountdownTimer` | `$1E` | vbi | key, vbi | the game-over countdown: $E2 steps, one every 8th jiffy (30 s) |
| `DliColors` | `$5E-$61` | key | dli1, dli2 | the four colours the display-list interrupts write (peach, red, gold, light green, faded by DRKMSK / COLRSH) |
| `GameState` | `$19` | key, vbi | key, newgame, vbi | 0 = game frame / countdown, 1 = copyright screen, 2 = wait for the copyright time, 3 = title, 4 = title after a game |
| `IntroRequest` | `$1C` | key, newgame, vbi | vbi | 1 after START, 2 after the board is set up ($A4B6): the frame routine begins the READY! intro when it sees 2 and clears it |
| `ItemColor` | `$A0` | newgame, vbi | dli1 | the colour of the fruit glyphs in the maze band: $44, or $DA on levels 6-9 |
| `KeyDebounce` | `$45` | key, vbi | key, vbi | decremented by every VBI; the key loop uses it to wait for CONSOL to settle |
| `Paused` | `$9B` | key, newgame, vbi | key, vbi | toggled by the key code $21 (the space bar) while playing; while set the frame routine only silences POKEY and stops: a pause. NOT tested live (no real key event reached the game, 21) |
| `StartLevel` | `$1B` | key | key, newgame, vbi | the start level chosen with OPTION at the title: 0, 1, 2, 4, 6, 8, 10, 12 |
| `TwoPlayers` | `$1A` | key | key, newgame, vbi | 0 = one player, 1 = two players (toggled by SELECT at the title) |

Reading it: the **keys** reach the frame handler through `GameState`, `Paused`, `TwoPlayers`, `StartLevel` and `IntroRequest` (set by the key loop, acted on by the frame handler); the **countdown** is shared both ways (`CountdownActive`, `CountdownTimer`); `KeyDebounce` is counted down by the frame handler and waited on by the key loop; **`DliColors`** are written by the key loop (the band colours, faded by `DRKMSK` / `COLRSH`) and read by the display-list handlers; `ItemColor`, written in the frame, is read by the first handler; `BandCounter` is the display-list handlers' own counter, cleared by the frame handler at its start and counted by the handlers.

## 5. The protocol, and the second player

- **Single bytes.** The hand-over variables of section 4 are one byte, or one byte per entry, written by a single store; on a 6502 a one-byte store cannot be seen half done. The multi-byte values (the pointers, the score, the timers of two bytes) are written and read inside the frame handler.
- **A new game is announced with a flag.** The key loop writes `IntroRequest` = 1 at START, runs the new-game sequence, and writes 2 at its end (`$A4B6`); the catalogue (`25`) says the frame routine begins the READY! intro when it sees 2 and clears it. The frame handler can run in between (the sequence takes frames). The measured sessions of `38` (219,987 frames, the start-ups among them) show no half-initialised frame, but **the interleaving of the sequence with the frame handler at every instruction was not run** (section 7).
- **Two players are not communication.** There is one machine, one stick port in use at a time (`STICK0,x`, x = the player on turn: `41`) and one display; the second player is the same game state with the per-player variables swapped (the `Player[2]` structure: `19`, `30`, `43`): `CurrentPlayer` is a variable of the frame handler, and the turn switch swaps the maze between `$0C00`, `$1000` and `$1400` (`SavedMaze1`, `SavedMaze2`). No second machine, no link, no network play, nothing sent anywhere; the high score is a status line, lost at power-off (no cartridge RAM, no disk).

## 6. The check on the machine

```
run: 1000 contexts runs (dli1 100, dli2 100, key 100, vbi 700); every cell read or written outside the stack and the ROM lies in the static set of its context: 0 outside
```

`tools/comm_map.py` runs each context from random states (the set-ups of `tools/iface_map.py`: the frame in six kinds and the running-game frame body, both display-list handlers, a pass of the key loop) with a probe on every read and write below `$4000`; `CurrentPlayer` is kept to 0 or 1. A pass of the key loop that starts a new game is checked against the key loop's and the sequence's sets together. The indexed clears of the new game and of `InitBoard` (`sta $20,x`, `$A47B`; `sta $80,x`, `$ADB4`; `$ADE3`) are given their spans from the code (`ldx #$1F`, `ldx #$7F`, `ldx #$13`); every other indexed zero-page access stayed inside the variable of its base address in the runs.

## 7. Limits

- **No race-freedom proof.** The protocol of section 5 is read from the code and the catalogue and seen in measured sessions; the check here shows what each context can touch, not that every interleaving of the new-game sequence with a frame gives the same game. A port that runs the key loop and the frame in two threads needs that proof; a port that runs them in turn does not.
- **A sample of states**: the dynamic check is a sample (as in `45`); the static sets are the claim.
- **The key loop is the original's**: a port's keyboard, console and joystick events replace it through the `Platform` of `45`; the variables of section 4 are the contract.
