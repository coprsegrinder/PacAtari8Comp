# 09 – Full Disassembly (Step C9)

Written 2026-11-10. Covers checklist stages 23–25 (disassembly produced, entry points, code/data split).

## Deliverables
- `src/asm/pacman.s` – the full ca65 listing of `Pac-Man.rom` ($A000–$BFFF), generated by `tools/make_asm.py`.
- `src/asm/pacman.cfg` – ld65 memory layout ($A000, 8,192 bytes).
- Helpers: `tools/probe_entry.py` (does this address look like code?), `tools/cov.py` (coverage and gaps).
- The listing is derived from copyrighted code; the repository stays private (owner decision).

## Method
Recursive descent (`tools/disasm6502.py`) from entry points whose evidence is recorded in `make_asm.py`:

| Address | Name | Evidence |
|---|---|---|
| $A386 | Start | cartridge RUN vector |
| $A6B4 | Init | cartridge INIT vector; the routine is just `RTS` |
| $A5FD | VbiHandler | `SETVBV` (A=7, X=$A5, Y=$FD) at $A460; ends with `JMP XITVBV` at $A60D |
| $A573 | DliHandler1 | VDSLST set to $A573 by `JSR $A6B5` at $A49B (X=$A3, Y=$73); saves A/X, ends `RTI` |
| $A5CE | DliHandler2 | same prologue/`RTI` shape, 47 bytes between the DLI and VBI handlers; installation still to be confirmed |

Also named: `SetDisplayList` ($A6B5, sets SDLST/DLISTL-H and VDSLST), and OS entry points `SETVBV`, `XITVBV`.

## Result
- **Code:** 2,925 instructions = 5,946 bytes (72.6%). **Data:** 2,246 bytes (27.4%), emitted as `.byte`.
- The data is two blocks: `$A000–$A385` (902 bytes, before the start routine; looks like encoded
  tables/maze data) and `$BAC0–$BFFF` (1,344 bytes; contains what look like character-set bitmaps,
  other tables, and the display list at `$BFA3` ending `41 A3 BF` = jump-and-wait-for-VBlank back to itself,
  followed by the cartridge header at `$BFFA`). Nothing is labelled yet (step C11).
- Smoke test: assembling `pacman.s` with ca65 and linking with ld65 gives a file with the **same SHA-256 as
  the original** (`a99b2dd1…8a56a`). The formal rebuild with a build script and test is step C10.

## Risks and caveats
- A trace can only prove bytes are *reachable as code*; it cannot prove that data was never misread as
  code. Any code that looks like data will be caught when the emulator coverage run (stage E17) shows
  what actually executes. Byte-exactness is unaffected either way.
- Code that is reached only through indirect jumps or computed addresses would still show as data.
  `jmp ($0026)` at $A0B0 is inside the $A000 data block (a coincidence in the bytes), not code.
- Correction made: `07-vectors-and-entry-points.md` wrongly said INIT sets the display list.
