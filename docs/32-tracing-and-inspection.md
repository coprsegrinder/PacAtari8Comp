## 1. The result

- **Stage 55, memory**: RAM snapshots of `$0000-$9FFF` at twelve events of the game (restart, board start, first dot, power pellet, ghost eaten, death, end of the frightened time, bonus item on and eaten, level complete, turn change, game over) - every byte that changes belongs to a variable or area of the catalogue (`25-variable-catalogue.md`) or to a documented OS class (section 5).
- **Stage 56, registers**: A, X, Y and S at the entry and at every RTS / RTI of every routine, in the running game, checked against the register claims of `23-function-table.md` (preserved registers, registers a routine never changes): section 6.

## 2. The method and its conventions

All tracing is done in **Altirra 4.40** (`external-tools/Altirra/`, NTSC, OS-B, the project's `Altirra_fast.ini` at about 7.5 times real time) through its debugger, started by `tools/run_patrol_trace.ps1 -Cmd altirra_X.cmd -Log analysis\raw-logs\X.txt -Seconds N` (`04-analysis-tools.md`). The ROM, the OS and the program are never modified; a harness may write the **emulated RAM or PC** (a test aid) and says so in its header.

| Command | What it does | Used for |
|---|---|---|
| `bt <addr> "fmt" args` | a tracepoint: print one formatted line each time the instruction at `addr` is about to execute | events, register and variable values at a place |
| `bp -n <addr> "cmds"` | a breakpoint that does not stop: run the commands (`r pc $...`, `eb $addr value`, `.echo`, `db addr Lnn`, `bc n`) | test aids, one-shot actions, snapshots |
| `bta r|w <addr> Lnn "fmt" args` | a memory-access trace: print a line at each read / write of the range | who touches a table or variable |
| `r @tN expr` | one of ten temporary registers | per-frame state of a harness (frame counters, windows) |
| `.echo`, `db` | print a text / a hex dump | markers and memory snapshots |

Rules that every harness of the audits of this chapter follows (each was learnt from a defect, see `OPEN-VERIFICATION.md` C-57):

1. **The sentinel** (OV-56): Altirra prints the first tracepoint hit of a session late - with the state of the *next* hit. Every audit puts `bt a386 "SENT ..."` (the entry of `Start`, the first game code to run) in front, so that its own line absorbs the error. A harness that reads its very first line without the sentinel can see wrong values in that one line.
2. **Register A is `@a`**: a bare `a` in an expression is the hexadecimal number 10. `x`, `y`, `s`, `p`, `pc`, `@frame`, `db($addr)`, `dw($addr)` are exact.
3. **Breakpoint numbers**: tracepoints and breakpoints are numbered in the order of definition, starting at 0 with the harness's own lines. A harness that clears its start breakpoint by number (`bc 0`) must stay the **first** `bp` line, and the one-shot lines of an audit (`bc <n>`) count the harness lines in front of them.
3. **Test aids are named**: the header of a harness lists what it writes to the emulated machine (a PC skip that makes Pac-Man immortal, a poke of the joystick shadow, a held timer). A claim made from a harness holds for the game's own logic only, with those aids.
4. **The log is flushed in 4 KB chunks**: the last lines of a run killed by the timeout may be missing; every analyzer tolerates a truncated last line.

## 5. Stage 55 - runtime memory inspection

## 6. Stage 56 - runtime register inspection

## 7. The pause key, live

The key loop of `Start` toggles `Paused` (`$9B`) when CH = `$21` (the space bar) and `$02F1` = 0 (`21-start-gameover-title.md`); while it is set the frame routine does `jmp ClearPokeyRegisters` and nothing else. This path was read from the code only (`25-variable-catalogue.md`). `tools/altirra_pause.cmd` writes CH := `$21` twice (as if the key were struck: frame 600 and 900) in a running game with a joystick bot and an immortal Pac-Man, and `tools/analyze_pause.py` checks the effect:
