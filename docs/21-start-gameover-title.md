# 21 - The Start of a Game, Game Over, the High Score and the Title Screen

Written 2026-11-11. Closes the three open points of `20-pacman-and-death.md`: (1) the high-score comparison at game over, the return to the title screen and what a key press does during the countdown, (2) the very first board start of a game with its start tune, (3) the test aids (a joystick bot, refilled lives, a PC jump that started the game).
Evidence: the code (`tests/test_start_gameover.py`, 5 tests) and **two long real sessions in Altirra** with 11 games started, 18 high-score calls (9 game overs), 9 countdowns (4 ran the full 30 s, 5 were ended by a key) and 25 key presses (`analysis/evidence-fullgame-summary.txt`, `analysis/evidence-fullgame2-summary.txt`; harnesses `tools/altirra_fullgame.cmd`, `tools/altirra_fullgame2.cmd`, analyzer `tools/analyze_fullgame_log.py`; the raw logs, 52 MB and 26 MB, stay local in `analysis/raw-logs/`).

## How the sessions were run (and what is still an aid)
Nothing in the game's memory is written and no program counter is moved. The only things injected are **the values the game reads from the controller registers, at the instructions that read them**: `STICK0` (the bot, direction only), the byte the game gets from `CONSOL` (`$D01F`: START = 6, SELECT = 5, OPTION = 3) right after the loads at `$A504`/`$A511` and while it waits for the release at `$A51C`, and the `STRIG0`/`STRIG1` shadows (`$0284`/`$0285`) before the loads at `$A4FA`/`$A4FF`. The key presses are scheduled from game state (`zp_1E`, `zp_19`, the number of games started), so they hit the same code a hand on the keys would.

| Aid | Used before | In these sessions |
|---|---|---|
| Joystick bot (`STICK0` poked every 48 frames) | death, restart, game-over runs | **still used**: it is input only, but it plays badly (scores 100-530, three digits only; a game lasts 3,000-4,000 frames) |
| Life counters refilled at each death | `altirra_death.cmd`, `altirra_afterdeath.cmd` | **gone**: every game ran 3 -> 2 -> 1 -> 0 (`analysis/evidence-fullgame-summary.txt`, "Lives") |
| Start of the game by moving the PC to `$A537` | all earlier harnesses | **gone**: START is injected at `CONSOL`; the PC jump reaches the same code but skips the debounce and the wait for the release (below) |
| Pac-Man invulnerable / frozen (`$A923` skipped, `zp_AA`) | screenshot and level harnesses | not used |
| A **real key event** (F2 posted to Altirra's window) | tried by `run_patrol_trace.ps1 -PressStart` | **does not start the game**: 0 games in 55,000 frames (session 2, first attempt). Synthesising keys by focusing the window would send them to whatever program is in front, so it was not done. |
| A human player | - | **none**. The bot and the register-level input stand in for one. |

## The very first board start (verified in 11 games)
Every game starts the same way, whether it begins from the title screen, from a countdown or in the middle of another game (`$A537` is the single entry). Frames counted from the `NEWGAME` event (the main loop reaches `$A537`):

| Frame | What happens |
|---|---|
| 0 | `$A537`: `zp_20` := 0, `zp_19` := 0, `zp_1C` := 1, restart at `$A477`: zero page `$20-$3F` cleared (this zeroes the life counters `$2C/$2D`), POKEY cleared (`ClearPokeyRegisters`, 8 writes), the maze copied from the stored original (`$0800` to `$0C00`, `$1000`, `$1400`), `InitBoard` (`$ADAF`), `Sub_ADF1`. One player: `Sub_A632` clears the score rows (`$2020`, `$202A` and `$2047`, 7 bytes each) and writes "00" (`$10 $10`) at `$202E/$202F`; two players: `Sub_A64E` clears `$202A` and `$2047`, draws player 2's row (`Sub_AD87`), writes "00" at `$204B/$204C` and then runs the same tail. The lives are 3 / 3 from frame 2. **The high score is not touched.** |
| 3 or 5 | `zp_1C` = 2 reaches `$A7C8` (in the per-frame routine): `zp_22` := 1, `ATRACT` := 0, `zp_1C` := 0, `DrawLevelIndicator` writes **READY!** (10 tiles at `$0DEF`; 10 writes). The 3-or-5 depends on where in the frame the main loop was. |
| 7 (or 8) | First tune step: the tune runs **only on frames where RTCLOK2 AND 3 = 0** (`$A7D3`), so every 4th frame, 64 steps. Each step writes `AUDF1`, `AUDF2` from `TuneAudf1` (`$BC50`) / `TuneAudf2` (`$BC90`) and `AUDC1` := `$A8`, `AUDC2` := `$A4`. |
| 167 | Step `$28` (the 41st write): `Sub_AD0E` draws the four ghosts and Pac-Man at their start squares and **decrements the life counter: 3 -> 2** (all 11 games; the second player's counter stays 3 until that player's turn). |
| 263 (264) | After step `$3F` the next tick finds `zp_A3` = `$40`: `zp_21` := 1, ghost 0 state := 1 (start route), `Sub_AD5E` clears the READY! row (14 writes). **The first move happens here: 263 frames (4.4 s) after the key.** |

Checks, all four hold in 11 of 11 games: the 64 steps come in order 0-63, **consecutive steps exactly 4 frames apart** (all 693 gaps), RTCLOK2 AND 3 = 0 at every step, **the 64 `AUDF1`/`AUDF2` values read in the game equal the ROM tables** (`TuneAudf1/2`), the sound writes are exactly 64 x each of `$A7E2`, `$A7E8`, `$A7ED`, `$A7F2` (plus the 8 clears; nothing else sounds). A frame-by-frame model of `zp_22`, `zp_A3`, `zp_21` from the READY! frame to the start of play matched **2,887 frames with 0 mismatches**. READY! to start of play was 260 frames in 8 games and 258 in 3, and the first tune step came 4 frames after READY! (2 in those 3), the difference being the 0-3 frame wait for the next RTCLOK2 tick.
Compared with the restart after a death (`20-pacman-and-death.md`, 66 frames, silent): the death restart never plays the tune because `InitBoard` clears only `$80-$FF`; `zp_21` and `zp_22` (below `$80`) stay 1. **The tune plays once per game**, after `NEWGAME`. A player's first board in a two-player game is the same start; the second player's first turn uses `zp_24`/`zp_25` (`19-two-players.md`) and has no tune (`Sub_AA2D`, `zp_25` = `$30`).
The sound was **not listened to** (register values only).

## Game over and the high score
`Sub_AA2D` reaches `$AAEF` when the player has no life left (`20-pacman-and-death.md`): GAME OVER tiles at `$0DED`, `COLOR3` := `$44`. In a one-player game, or after the last of the two players has died (`zp_23` = 0), it then calls `Sub_AB26` twice: `X` = `$2A` (player 1's six score digits at `$202A-$202F`) and `X` = `$47` (player 2's at `$2047-$204C`), against the **high score at `$2039-$203E`**. When player 1 dies first in a two-player game, the GAME OVER text is drawn while player 2 still plays (`zp_23` = 2, 2 events in session 2) and **no comparison is made** (`$AB06`: `zp_23` <> 0 -> return).
**`Sub_AB26`** (`$AB26-$AB47`, 34 bytes): the digits are screen codes (`$10`-`$19` for 0-9, `$00` for a leading blank). From the left, digit by digit: equal -> next; the score digit smaller -> return, nothing changes; greater -> **copy this digit and all digits to its right** into the high score and return. All six equal -> return. So the comparison is a plain numeric one because a blank (`$00`) is smaller than any digit, **a score of "00" beats an empty high score**, and the score is never added, so the high score is always one of the two scores.
**Live: 18 calls in 9 game overs (session 1: 14 calls in 7 games; session 2: 4 calls in 2 games), the model matched 18 of 18** (new high score and path): player 1 copy 4 (3 digits each time), equal 1, less 4; player 2 less 9 (in one-player games the player-2 row is all blank). Player 1's call always came first, player 2's in the same frame or the next. The high score was written **only by `$AB3E`** (12 writes in 4 copies) and never decreased in 180,552 frames. In a two-player game over both scores are compared (151210 -> high score; 111010 smaller).
Not seen live: a player-2 score greater than the high score; scores of different length (all bot scores are three digits, 100-530); an exact tie of two non-zero scores in two-player mode. The model and the code cover them (`tests/test_start_gameover.py`: tie, longer score, blank high score).
**An abandoned game is not compared.** SELECT or OPTION pressed during play (below) leaves the game for the title; the score of that game (100 points in the run) never reached the high score (still 0). The same holds for START pressed during play.

## The 30-second countdown (9 countdowns: 4 ran to the end, 5 were ended by a key)
After the compare: `zp_24` := 0, `zp_20` := 1, `zp_1E` := `$E2` (226). The per-frame routine (`$A78C`) decrements `zp_1E` **on frames where RTCLOK2 AND 7 = 0**: **226 -> 0 in 226 steps, 8 frames apart (224 of 224 gaps in every full countdown)**, 1,802 frames from the game-over frame to the last step (30 s); the model matched every one of the 11,647 frames of the 9 countdowns with 0 mismatches. The screen stays as it is (GAME OVER in red, lives, scores, the last dots).
When `zp_1E` reaches 0 the **main loop** (`$A4ED`) sets `zp_19` := 4 and `ATRACT` := 4 (`$A4F1`/`$A554`): `COUNTDOWN_DONE` and the new state in the same frame, **the title is on screen one frame later**.

## The return to the title screen (state 4)
`Sub_A6CC` (the deferred VBI, `zp_19` <> 0) draws the title every frame in states 3 and above. Observed at the first frame of state 4 (four waits of 200, 90,632, 200 and 36,994 frames): display list `$BFA3` (the maze) -> **`$BF81` (the title)**, colours `COLOR0-3` `86 0C 00 44` -> **`DA 0C 00 2A` = `ColorsTitle` (`$BBEA`)** (the colours are logged at the start of each frame, so the new values show one frame after the state changes), `ATRACT` = 4, **the last game's scores stay on the screen and the high score is shown next to them**, `zp_20` stays 1, `zp_1E` = 0. State 4 differs from state 3 in one thing: **`Sub_A632`/`Sub_A64E` run only in state 3** (`$A726`: `CPY #3`), so in state 4 the old scores are kept, in state 3 they are cleared to "00".
**Nothing else changes while the title waits: no demo, no timeout, no return to the first title.** In the longest wait, 90,632 frames (25 minutes), the only variables that changed were the OS's `ATRACT` (+1 about every 256 frames, 254 at the end; from `$80` the OS rotates and dims the colours, an OS function) and the debounce counter. The game leaves state 4 only by a key.

## Keys: what each does (all verified live unless marked)
The main loop checks, in this order (`$A4C8-$A559`): **if `zp_19` <> 0 or the countdown is running (`zp_20` = 1, `zp_1E` <> 0): `STRIG0` = 0 or `STRIG1` = 0 -> new game at once**; then `CONSOL`.
During normal play (`zp_19` = 0, `zp_20` = 0) **the trigger is not looked at** (the loop goes straight to `CONSOL`).

| Key | During the countdown (state 0, `zp_20` = 1) | In play | At the title |
|---|---|---|---|
| **STRIG0 / STRIG1** (fire) | **New game in the same frame, while held** (STRIG0 at `zp_1E` = 150: +0 frames; STRIG1: +0) | no effect (code; not pressed live) | **New game** (state 4: +1 frame after the first frame held) |
| **START** | **New game on RELEASE**: the key is held until `A51C` sees `CONSOL` change; held 51 frames: new game 2 frames after the last frame held; held 64 frames: 1 frame after (7 START presses) | **New game** (the running game is dropped, no compare; verified: START at play frame 300) | New game on release (the debounce loop at `$A511`, `zp_45`, runs first) |
| **SELECT** | **Opens the title menu in state 3**; nothing else changes: `zp_1A` and the start level stay (the toggle code at `$A544` is reached only when `zp_19` >= 3) | **Leaves the game for the title menu** (state 3); score not compared | state 3 or 4: **toggles one/two players** (`zp_1A` 0 -> 1 verified, state 3) |
| **OPTION** | as SELECT: **title menu in state 3**, no change of the start level | as SELECT (verified, OPTION at play frame 600: title 2 frames after the release) | **StartLevel** `zp_1B` steps 0, 1, 2, 4, 6, 8, 10, 12, 0, 1, ... (10 presses seen, `$A559`) |

Details seen in the logs:
- **From the countdown, SELECT or OPTION enter state 3**: `zp_19` := 3, `ATRACT` := 3 (events `SET_Z19` at the release), the countdown **freezes** (`zp_1E` stays 92 for 171 frames, both times), `Sub_A632` runs each frame and clears the old score to "00" **in the first frame**; the high score stays. The following START starts a new game, and **`zp_1E` keeps counting down from its frozen value during the new game** (92 -> 0 harmlessly; `zp_20` = 0, and the next game over reloads 226). The same drain happens after STRIG/START in the countdown (92 and 150 seen).
- **New game, in every case**: lives 0 at the first frame (`$20-$3F` cleared) then 3/3, scores "00", the high score kept, the tune and READY! as above, level counters = `zp_1B` (**start level 2: both counters 2**, so the first board is the level-3 board in the game's numbering; `14-levels.md`).
- **Two players** (`zp_1A` = 1): `Sub_A64E`; the lives go (3,3) -> (2,3) at the start tune, (2,2) at player 2's turn start, then alternate with each death: (1,2), (1,1), (0,1), (0,0) (2 two-player games, `19-two-players.md`).
- The press schedule hit the intended window in all 25 presses (7 START, 4 trigger, 12 OPTION, 2 SELECT) (first reaction at the release, at the next tick, or at once for the triggers).
- Not tested live: SELECT/OPTION in title state 4 (code: the same `$A544`/`$A559` and then `$A550`: state 3); pressing keys in the very first frame of the game over; the keyboard itself (a real key event did not reach the game, see the aids).

## What was verified how
- **Static** (`tests/test_start_gameover.py`, 5 tests): the code bytes of the main-loop checks, the new-game entry, the SELECT and OPTION handlers, the countdown, the READY! and tune code, the game-over code and `Sub_AB26`; the tune tables; the compare model (equal, copy, less, longer score, blank high score).

## Simulation of the remaining cases (2026-11-11)
`tools/altirra_p2win.cmd` + `tools/analyze_p2win.py`, log `analysis/raw-logs/p2win.txt` (74,281 frames), result `analysis/evidence-p2win-summary.txt`. No human: the joystick bot and the key values at the controller registers as in the other sessions, plus **one aid**: player 2's score bytes (`$2049-$204C`) are set once to 1500 after 300 frames of player 2's play, because the bot cannot score that. Everything else is the game's own code.
Sequence and result: game A (one player) ends with a score of 100 and sets the high score to 100; after the full 30 s countdown the title is in state 4; **SELECT in state 4** leaves it for state 3 and switches to two players; game B (two players); at game over `Sub_AB26` runs for player 1 (400 over 100: 3 digits copied) and then for player 2 (**1500 over 400: 4 digits copied, starting at the first greater digit**), the new high score is 1500, and the model and the log agree on both calls; after the second full countdown **OPTION in state 4** leaves it for state 3 and raises StartLevel from 0 to 1. The high score bytes were written only from `$AB3E`. A SELECT or OPTION press in state 4 therefore behaves like one in state 3 (as the code `zp_19 >= 3` predicts).
