# 29 - The Pointers (stage 46)

GENERATED by `python -I tools/analyze_pointers.py --write docs/29-pointers.md` from the trace of `src/asm/pacman.s`, the routines of `23-function-table.md`, the variables of `25-variable-catalogue.md` and `analysis/evidence-pointers-summary.txt` (the emulator measurement). Tests: `tests/test_pointers.py`.

## 1. The result

- The code has **31 indirect instructions**, all of the form `lda (zp),y` (17) or `sta (zp),y` (14). There is **no `(zp,X)` addressing and no `JMP (abs)`**, so no pointer is ever executed: **every pointer is a data pointer** and the control flow is fixed (`28-stack.md`, `23-function-table.md`).
- There are **6 pointer variables** (12 zero-page bytes, low byte first): `SrcPtr`, `DstPtr`, `MazePtr` and, for one routine each, `PopupMissilePtr`, `PopupPlayerPtr` and `ClipPtr`. Nothing else in the zero page is used as a pointer.
- A pointer is always loaded **in two stores, low byte then high byte** (or by a 16-bit increment / decrement), and the index Y is a loop counter or a constant: the instruction before each loop is the measurement probe of section 6.
- Besides the zero-page pointers there are **4 tables of 16-bit addresses** in ROM (23 entries; each target is named in section 4), the **16-bit operands of the two display lists** (section 5), the two cartridge vectors, and the three pointers the code gives to the OS and ANTIC (section 5).
- Every pointer value is computed at run time from a **constant, a table entry or the position of an entity**; none is kept in game state across frames except `MazePtr` (the cell of Pac-Man). The port needs one pointer type for the whole address space (section 7).

**A stray copy into the ROM.** `InitDisplay2` (the title and attract screen set-up) does not end with `rts`: its last instruction is `jmp $B985`, the middle of `StepAndDrawEntity`. That tail sets `DstPtr` high = `$24 + X` and copies 16 bytes `(SrcPtr),y -> (DstPtr),y`. X is still `$81` (the argument of `SetDisplayList`), so `DstPtr` is `$A5xx`: **a 16-byte copy into the cartridge ROM**, which the hardware ignores. Nothing is changed and no value is used, so it is harmless; the port must not reproduce the write (it has no effect) and must not call a ghost-drawing routine from the title set-up. The measurement (section 6) shows it at every entry of `InitDisplay2`.

## 7. What the port does with this

- One flat 64 KB `uint8_t mem[65536]` with the pointers as **`uint16_t` offsets** into it is the exact image of the original: `SrcPtr`, `DstPtr`, `MazePtr`, `ClipPtr`, `PopupMissilePtr`, `PopupPlayerPtr` become `uint16_t` variables, `(zp),y` becomes `mem[ptr + y]`, and the 16-bit increments are ordinary 16-bit adds (the stores come in pairs). The values should not be C pointers while the equivalence tests (stages 86-87) compare the RAM state.
- A pointer to ROM data (`SrcPtr` from `PacShapePtrs`, `GhostScorePtrs`, the streams) can become a typed C pointer or an index into the data array of the port **only** if the asset format of stages 69-70 keeps the offsets; the pointer tables of section 4 are then arrays of indices.
- `JunctionRowPtrs` and `StartRoutePtrs` point into **RAM** tables ($0600-$06FF, filled from the nibble tables at start): in C they are two-dimensional arrays and the pointer tables disappear.
- `PopupMissilePtr`, `PopupPlayerPtr` and `ClipPtr` are **locals** of one routine (`27-local-variables.md`): an index into the missile / player page.
- `MazePtr` is **state** (kept between frames): in C it is the offset into the maze array, or the pair (column, row) of Pac-Man's cell, updated by +-1 per 4 pixels sideways and +-40 per row (section 3); the two tunnel assignments (`$8F`, `$B7`) are the wrap of the column.
- The display-list operands are the screen addresses ($2000, $1C00, $0F70, $0C00): the graphics layer of the port (stages 79-80) needs them as the screen base addresses; the OS vector writes become the registration of the two display lists and the two interrupt handlers.
