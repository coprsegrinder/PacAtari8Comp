# 30 - The Structures (stage 48)

GENERATED by `python -I tools/analyze_structures.py --write docs/30-structures.md` from the trace of `src/asm/pacman.s`, the routines of `23-function-table.md`, the variable catalogue of `25-variable-catalogue.md` (`tools/analyze_variables.py`) and `analysis/evidence-structures-summary.txt` (the emulator measurement). Tests: `tests/test_structures.py`.

## 1. The result

- The ROM has **no structures and no record-shaped data in the zero page**: every object is kept as a **structure of arrays**, one zero-page array per field with stride 1 (`EntityX`, `EntityY`, `EntityDir`, ... at `$8A`, `$85`, `$8F`), indexed by the object number in X. There are **25 arrays** (`25-variable-catalogue.md`), indexed by **191 instructions** `sta/lda array,x`; **no instruction reaches a field of one object through another** (no `EntityX-1,x` or `+k` offsets) **except `GhostTimer+1,x`** in `SetReleaseTimers`, which stores the release timers of ghosts 1-3 (section 2).
- The objects are: **Entity** x5 (ghosts 0-3 and Pac-Man = 4), **Ghost** x4, **Player** x2; and nine single objects (PacMan, GhostShared, Frighten, Bonus, Death, Sound, Flow, Display, Scratch) plus the pointers and the OS variables. **All 109 zero-page variables (184 bytes) belong to exactly one structure** (section 3; the check is in `tests/test_structures.py`).
- The object index is **the same number everywhere**: ghost g = player page `$24+g` = colour register `PCOLR0+g` = `HPOSP0+g`; Pac-Man = 4 = the missile page `$23` (the page is computed as `$24 + X` with X = $FF for Pac-Man in `ClipEntityAtTunnel`, `29-pointers.md`). `CurrentPlayer` (0, 1) is the index of every per-player array.
- **Lifetime** follows the memory map: `$80-$FF` is cleared at every `InitBoard` (and the first 20 bytes loaded with the start positions), `$20-$3F` at every game start, the rest is kept (section 5). Measured in Altirra (section 8): the index of every array access stays in the range of its array, and the state after `InitBoard` and after the game restart is what section 5 says.
- For the port: **an array of structures** (`Entity entity[5]`, `Ghost ghost[4]`, `Player player[2]`) replaces the structure of arrays; the equivalence tests (stages 86-87) read the original RAM image, so the port keeps a **mapping function** per field (original address = base + index; the table of section 3) rather than the original layout.

## 4. The initial state of the entities

`InitBoard` copies the 20 bytes of `ZeroPageInit80` (`$BB6F`) to `$80-$93`: that is `PacMan.maze_ptr`, `PacMan.sub_x`, `PacMan.last_cell_y`, `PacMan.last_cell_x` and the three entity arrays. Decoded:

- `PacMan.maze_ptr` = `$0E93`, `sub_x` = 2, `last_cell_y` = $A6, `last_cell_x` = $7A

| Entity | Object | y | x | dir |
|---|---|---|---|---|
| 0 | 0 (red) | $64 | $7C | 4 (left) |
| 1 | 1 (pink) | $74 | $7C | 2 (down) |
| 2 | 2 (green) | $74 | $70 | 1 (up) |
| 3 | 3 (gold) | $74 | $88 | 1 (up) |
| 4 | 4 Pac-Man | $A4 | $7C | 4 (left) |

Ghost 0 starts in the corridor above the ghost house (y $64), ghosts 1-3 inside the house (y $74) at x $7C, $70, $88; Pac-Man starts below it (y $A4, x $7C) facing left. `MoveDelayCount[0..3]` (the ghosts) and `[4]` (Pac-Man) are loaded from `MoveDelay` by level; `GhostTimer[1..3]` from `HouseReleaseTimers`; everything else in `$94-$FF` is 0.

## 5. Lifetimes: what the code resets

| Range | Class | Reset by |
|---|---|---|
| `$18-$1F` | start-up | cleared once by the cold start (`Start` $A395, X = $27..0 stores A = 0 in $18-$3F) |
| `$20-$3F` | game | cleared at every start and restart of the game (`$A47B`: X = $1F..0 stores 0 in $20-$3F), then set by NewGameInit / ClearPlayerCounters |
| `$80-$FF` | board | cleared by InitBoard (`$ADB4`: X = $7F..0 stores 0 in $80-$FF; called by Start, FrameDispatch and TurnControl: the first board, a new board, a new life, a turn switch); $80-$93 are then loaded from `ZeroPageInit80`, `MoveDelayCount` and `GhostTimer`[1..3] are set |
| the rest (`$00-$17`, `$40-$7F`) | kept | no bulk write; these are the OS bytes (`POKMSK`, `RTCLOK2`, `ATRACT`, `DRKMSK`, `COLRSH`), `KeyDebounce`, `KeyValue`, the pointers `$38-$3F`/`$47-$48` (set before use), `HalfSpeedToggle` and `DliColors` |

Callers of the routines that reset: `InitBoard` is called by FrameDispatch, Start, TurnControl; `NewGameInit` by Start; `NewBoardInit` by AdvanceLevel, FrameDispatch; `ClearPlayerCounters` (per player: `pellets` = $0F, `bonus_count` and `dots_eaten` = 0) by NewGameInit, **and by falling through from the end of `NewBoardInit`** (`$AE1C`: `ldx CurrentPlayer`), so the per-board counters of the player on turn are reset at every new board; `SetReleaseTimers` by InitBoard, NewBoardInit, NewGameInit.

What this means for the structures: `Entity`, `Ghost`, `PacMan`, `GhostShared`, `Frighten`, `Bonus`, `Death` and the Sound state are **per-board** (re-initialised by one `memset` and the start-position copy); `Player` and `Flow` are per-game; the pointers and OS bytes are not game state. In C: `memset(&board_state, 0, sizeof board_state)` then the initial values of section 4 reproduces `InitBoard`, if the per-board structures are kept together in one block.

## 6. Objects that are not zero-page arrays

**The player-missile memory** (`PMBASE` = $20, 256 bytes per object, one byte per scan line; the picture of an object starts at row `Entity.y`):

| Page | Object |
|---|---|
| `$2300` | Pac-Man (`Entity[4]`) and the pop-up digits: the four missiles, two bits each; `Entity[4].y` is the row of the first picture line |
| `$2400` | ghost 0 (player 0, `Entity[0]`) |
| `$2500` | ghost 1 (player 1) |
| `$2600` | ghost 2 (player 2) |
| `$2700` | ghost 3 (player 3) |

**The picture buffers** (RAM, one byte per picture row, copied 16 rows to the page at `Entity.y` by the drawers): `$0400-$040F` Pac-Man's (his 10 shape rows at `$0403-$040C`, copied by `DrawAllInPlace` from `PacShapePtrs[dir] + mouth offset`), `$0410-$041F` a ghost's (shape rows `$0412-$041B`, feet row `$041C`, copied by `StepAndDrawEntity` from `$BAC0 + A`).

**Saved mazes and the screen**: `WorkingMaze` `$0C00-$0FFF` is the working maze **and** the screen of the maze band (23 rows of 40 bytes: the dots, walls and power pellets; `PacMan.maze_ptr` points into it); `SavedMaze1` `$1000-$13FF` / `SavedMaze2` `$1400-$17FF` are the two players' mazes while the other plays (`Copy0C00To1000` / `Copy0C00To1400`); `OriginalMaze` `$0800-$0BFF` is the stored original. So **a Player is (the 6 fields of section 3) + one 1,024-byte maze**; the working maze is the maze of `CurrentPlayer`. The score of a player is not a field of the zero page: it lives as digits in the status row (`StatusRow`, `25-variable-catalogue.md` section 3; `19-two-players.md`) and is added to with `ScoreAdd[0..5]` by `AddToScore`.

**RAM tables built at start-up** (from the nibble tables, `12-data-formats.md`) and their records:

| Table | Address | Records x bytes | Size | What |
|---|---|---|---|---|
| DeathPlotRows | `$0600` | 14 x 1 | 14 | one nibble per death-animation frame: the row plotted |
| JunctionExits | `$060E` | 10 x 10 | 100 | 10 rows x 10 columns of direction masks (1 up, 2 down, 4 left, 8 right): the exits of each junction of the maze lattice |
| FrightenEndPhase | `$0672` | 20 x 1 | 20 | by level: the FrightenPhase value at which the frightened period ends |
| StartRoutes | `$0686` | 40 x 1 | 40 | four routes of 13, 8, 8, 11 direction-per-junction steps, each ended by $F; the pointers are `StartRoutePtrs` |
| PatrolRoutes | `$06AE` | 230 x 1 | 230 | 16 zero-terminated closed routes; `PatrolRouteOffsets` gives the start of each |
| BonusScore | `$0794` | 13 x 2 | 26 | by level: (thousands, hundreds) digit pair |
| MoveDelay | `$07AE` | 24 x 1 | 24 | frames per step in four-step cycles, chosen through `PacMoveDelayBase` / `GhostMoveDelayBase` |
| NoReverseMask | `$07C6` | 9 x 1 | 9 | by direction: the mask that forbids reversing |
| ReverseDir | `$07CF` | 9 x 1 | 9 | by direction: the opposite direction |

**Records in ROM:**

| Table | Address | Records x bytes | What |
|---|---|---|---|
| PatrolStartPositions | `$BCEE` | 16 x 2 | (x, y) of the junction where each patrol route starts |
| CornerPositions | `$BD0E` | 4 x 2 | (x, y) of the four corners the ghosts go to |
| BonusScoreGlyphs | `$BD45` | 8 x 5 | five glyph codes per bonus score (100 300 500 700 1000 2000 3000 5000) |

**Pictures** (ROM, one byte per row; the row count is the record size): GhostShapeUp `$BAC0` x 10; GhostShapeDown `$BACA` x 10; GhostShapeLeft `$BAD4` x 10; GhostShapeRight `$BADE` x 10; GhostShapeFrightened `$BAE8` x 10; GhostEyesShape `$BAF2` x 10; PacShapeFull `$BAFC` x 10; PacShapeRight1 `$BB06` x 10; PacShapeRight2 `$BB10` x 10; PacShapeLeft1 `$BB1A` x 10; PacShapeLeft2 `$BB24` x 10; PacShapeUp1 `$BB2E` x 10; PacShapeUp2 `$BB38` x 10; PacShapeDown1 `$BB42` x 10; PacShapeDown2 `$BB4C` x 10; StarShape `$BC07` x 12; GhostScoreZeros `$BC13` x 12; GhostScore200Digits `$BC1F` x 12; GhostScore400Digits `$BC2B` x 12; GhostScore800Digits `$BC37` x 12; GhostScore1600Digits `$BC43` x 12.

- **Every index stays in its array**: 0 accesses outside, in 93 million hits at **all 191 sites**. - **After the restart clear** (29 snapshots): `$20-$3F` is 0 in all 29. Every harness now starts with a sentinel tracepoint on `Start` that absorbs it (`04-analysis-tools.md`, OV-56 / C-57).
