So the work is of three kinds: **(1)** translate what is already checked into C and check the C against the same vectors (stages 75-77); **(2)** write, in Python first, what is not yet written, checked against the ROM, so that the oracle chain `ROM - Python - C` holds for the whole game (stage 78), then translate it (stage 79); **(3)** the parts that are not game logic (stage 80). Writing the application layer in Python before C is deliberate: the C is then never the first version of anything, and every C function has a twin that was compared with the ROM.

## 2. The oracle chain and the vector files (the rule for every C stage)

`ROM -- concrete 6502 -- Python port form -- vectors -- C`. A **vector** is one call: the World image before (the whole state: zero page, maze, status rows, shadows, pages, positions, picture buffers), the RANDOM values supplied, the arguments, and the World image after plus the ordered chip writes and the number of RANDOM values used. The Python checkers that already compare the port with the ROM write the vectors from the same random states (`tools/make_vectors.py`, stage 75b); the C runner loads them, runs the C function, compares everything. Because the Python port is already 0 differences against the ROM on those states, a C function with 0 differences on the vectors is equal to the ROM on them. A vector file is **derived data** (like the asset pack): generated locally, not committed.

Every sub-stage ends with: the C compiled with `-std=c99 -Wall -Wextra -Wpedantic -Wconversion -Werror` by clang **and** gcc, **the portability scan and the file sandbox test of section 2a passing**; the vectors of its functions run by `ctest` with 0 differences; a **negative control** (a deliberately broken function is caught); a register row (C-nn) and a `PROGRESS.md` row; **nothing committed** unless asked.

## 2a. Constraints from the owner (2026-11-18, `49`)

**Portable.** The game logic (`core/`, `app/`) is standard C99 with the fixed-width types of `<stdint.h>` and nothing else from the system: no POSIX, no Win32, no compiler extension, no `printf` of a pointer, no assumption about the byte order, the size of `int` or the signedness of `char`; bytes are written and read one at a time (the vector files, the asset blob and any save file have a defined little-endian byte format). Everything that touches the operating system - the clock, the keyboard and pad, the window or framebuffer, the audio device, **files** - is behind the `platform/` layer (`hal.h`), so that a port to another system replaces `platform/` and the shell only. Checked by `ctest`: (a) the C99 build with `-std=c99 -pedantic -Werror` by clang and gcc (stage 73), (b) **a source scan** (`tests/portability_scan`, a CMake test) that fails on any system header, any `__attribute__` / `#pragma` / inline assembly or `asm`, any non-standard integer type, and any use of a file or process function outside `platform/`, (c) a **byte-order test**: the runner and the loaders produce the same vector and blob results when the byte-order assumption is deliberately swapped in the test build (`PM_TEST_SWAP_ENDIAN`), (d) a size test (`static` asserts on the widths that the 6502 arithmetic relies on, `tests/toolchain_check.c`). Only clang and gcc on Windows are available here: a second operating system is not tested, and the plan says so rather than claims it.

**Writes only in the main folder or below.** The port opens files through **one module**, `platform/fs.c` (`pm_fs_open(relative_path, mode)`), that works on a **relative path under the main folder**, normalises `\` to `/`, and **refuses** an absolute path, a drive or UNC prefix, a `..` component and a path through a link it can see; the main folder is where the executable is started from by default and can be set by one option, never from the environment. Nothing else in the C code may call `fopen`, `remove`, `rename`, `tmpfile`, `getenv("TEMP")` and the like (the source scan above). What the port may write, and where: the high score and the options (`save/`), logs and per-frame state dumps of the replay shell (`logs/`), the asset blob and the vector files the tools make (`resources/`, which is git-ignored), the build (`build/c/`). The Python tools that produce vectors and blobs follow the same rule for what they hand to the C (`resources/`, `build/`); the temporary files of the existing Python tests are not part of the port and are left as they are. A test (`tests/fs_sandbox`) tries 30 escaping paths (absolute, `..`, `a/../../b`, drive letters, UNC, long paths, embedded NUL) and must be refused, and checks that an allowed write lands where it should.

## 7. Risks, from what the earlier stages found

- **The application layer is the largest unknown**: its drawing writes screen cells of several screens (`42`) and its timing was measured, not modelled; hence stage 78 in Python first, with the 15 frame classes as strata.
- **The handler that outlasts the objects' lines** (`50`): the original's collision registers are a mixture of two scenes in those frames; the C port gives the full-frame answer; equivalence on those frames is a question for stages 86-87 and 90 (listed in `50` section 6), not for 75-80.
- **`RANDOM`** (D1) and **PAL** are not covered by any oracle beyond the measured sessions.
- **A second operating system** (section 2a): there was none for stages 75-87, so portability was argued by the scan, the byte-order test and the strict C99 build. **Stage 88 found one: WSL2 with Ubuntu and gcc**, where the port builds and plays identically after one fix (`54`); macOS, MSVC, 32-bit, big-endian and ARM remain untested (OV-72).
- **Sound** is verified against recordings, not against a 6502 comparison: a different kind of oracle (`22`).
