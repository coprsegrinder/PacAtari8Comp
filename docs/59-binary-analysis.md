## 2. How the binary was taken apart

**Method** (`08`, `09`, `10`): a recursive-descent disassembler for the documented 6502 instruction set (`tools/disasm6502.py`, validated against the instruction set, `tests/test_disasm6502.py`) follows every branch, `JSR` and `JMP` from five entry points whose evidence is recorded; whatever it cannot reach is data. The listing `src/asm/pacman.s` is generated (`tools/make_asm.py`) with labels and names from `tools/labels.py`, assembles with ca65 / ld65 and **rebuilds the ROM byte for byte** (`tools/build_rom.py`, `tests/test_rebuild.py`: same size and SHA-256).

|---|---|---|
| Start | `$A386` | the cartridge RUN vector (`$BFFA`) |
| DliHandler1 | `$A573` | `VDSLST` set to `$A573` by the call at `$A49B`; saves A and X, ends `RTI` |
| DliHandler2 | `$A5CE` | the same prologue and `RTI` shape; the second display-list handler, between the first and the vertical-blank handler |
| VbiHandler | `$A5FD` | `SETVBV` (A=7, X=`$A5`, Y=`$FD`) at `$A460`; ends with `JMP XITVBV` at `$A60D` |
| Init | `$A6B4` | the cartridge INIT vector (`$BFFE`); the routine is a bare `RTS` |

**Result:**

- **2,925 instructions, 5,946 code bytes** (72.6% of the ROM), all in **one block, `$A386-$BABF`**; the data is in the two blocks around it: `$A000-$A385` (902 bytes: 3 bytes no code reads, then the character-set stream and the maze stream) and `$BAC0-$BFFF` (1,344 bytes: the ghost and Pac-Man pictures, the junction and sight tables, the colours, the score digits, the tune, the texts, a stream, the two display lists and the cartridge header). **2,246 bytes of data in 79 named regions**; the code and the regions **account for every byte of the ROM** (5,946 + 2,246 = 8,192: no byte uncovered, none counted twice, `09`, `47`).
- Every one of the instructions was also **run** in the real machine or on the 6502 interpreter, except 5 that are dead paths of the original (`32`); every `JSR` site ran (`32`).

## 7. What reverse engineering found

| Finding | Where it is shown |
|---|---|
| An 8 KB image whose two 4 KB halves differ (consistent with the two-chip retail cartridge); RUN and INIT are in the header at `$BFFA`; INIT is a bare `RTS` | `07`, `03` |
| The vertical-blank handler is installed as a **deferred** VBI (`SETVBV` with A=7): the whole game frame is one routine, `FrameDispatch`, and the main program only runs between frames | `07`, `24`, `38` |
| Every `JSR` and `JMP` target is static: no indirect jump, no push-and-return trick, no `BRK`; the call tree is complete | `23`, `28` |
| 6 routines are not reducible: a loop with a second entry through `lda #imm / bne` | `26` |
| 39 routines had no name from the start (`Sub_XXXX`); they were named from their behaviour, evidence in the chapters | `11`, `24` |
| The data is packed: the maze, the character sets and the move-delay tables are nibble and run streams that `Start` expands into RAM | `12` |
| The level-dependent tables are indexed past their ends on boards above 15: the real game reads the bytes that follow | `14`, `44` |
| `PCOLR0-3` = `$DC` carries which ghost was eaten across the pause: a colour shadow used as a variable | `45` |
| Two stray writes: `InitDisplay2` writes 16 bytes into the ROM (ignored by the machine), a black band-1 colour writes `$D111` | `42` |
| A race at `$A800` (ghost 0 incremented twice) that is a path of the search no game can take | `34` |
| The extra life is decided by the screen cell of the ten-thousands digit, not by the number: it can be given at a score wrap | `44` |
| 5 instructions are never executed in any run: dead paths of the original, shown from the code | `32` |
| The game's RANDOM is read at exactly 3 places | `31` |
| The time budget of the handler is not provable by static analysis (the play frame's bound is 2x the budget); the heaviest play frame found costs 89% of it | `39` |

## 8. How this was checked

- The disassembler decodes every opcode of the documented set and nothing else (`tests/test_disasm6502.py`); the listing assembles to the original, byte for byte (`tests/test_rebuild.py`); the named zero-page bytes rebuild the same ROM (`tests/test_zp_names.py`).
- The control flow was cross-checked: the recursive trace, the live sessions (36 sessions, 2,920 of 2,925 instructions, `32`) and the static / dynamic comparisons of `26`, `28`, `46`.
- This chapter is regenerated from the ROM and the tools: `tests/test_binary_docs.py` fails if the numbers or the tables change.
