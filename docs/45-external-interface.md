GENERATED by `python -I tools/iface_map.py --write analysis/evidence-iface-summary.txt` and `python -I tools/analyze_iface.py --doc docs/45-external-interface.md` from the static classification of the 2,925 instructions of the ROM (`tools/iface_map.py`), its run on the concrete 6502, `tools/platform_iface.py` and the curated text of `tools/analyze_iface.py`; tests: `tests/test_iface.py`. ## 1. The result

- **The game takes 14 things from the outside** (section 2), read by **35 instructions** of the ROM: the joystick, the two triggers, the keyboard code and its delay, the console keys, three GTIA collision registers, `RANDOM`, the jiffy clock and three OS variables (`POKMSK`, the two attract-mode values); and one thing it reads back of its own: the player colour shadows (section 4). **Nothing else reaches it.**
- **The list is closed, and this was run, not only read** (section 3): 3000 random game states (the frame in every mode, the two display-list handlers, a pass of the key loop, the running-game frame body) were each run twice, the second time with **every external cell that is not a declared input** (page 2 and page 3, the hardware registers, the OS ROM: up to 11,000 cells) holding other random values: **0 differences** in the RAM, in the ordered writes to the outside, in the RANDOM reads and in the OS calls.
- **Every declared input is live** (section 3): changing one alone changed the result in some runs, for each of them (the table of section 3; `POKMSK` is read only by `Start`, which these entries do not run).
- **There is nothing else**: the game makes **2** control transfers outside the cartridge (`SETVBV`, `XITVBV`), has no indirect jump, no BRK, and **no file, device, serial, network or PIA access** of any kind (section 5). "No files, no network" is a measured fact of the code, not an assumption.
- **One finding for the port's state** (section 4): the game keeps one piece of state in the OS page, **the ghost colour shadow `PCOLR0-3`**: `GhostEaten` writes `$DC` into the eaten ghost's shadow and the end of the pause finds the ghost by looking for it (`$B09D`). It is state of the eaten-ghost pause; the port's save state must carry it if it saves in the pause (`43`, section 8).
- **What the port implements** (section 7): `tools/platform_iface.py`, a `Platform` class with one method per declared input, a scripted implementation, and `run_frame(w, platform)`, which runs one frame of the port-form game (`44`) on a platform. The **collision registers** are an input the port must compute from the sprite pictures: that model is built and equals the GTIA's (OV-68, closed in `50`); the scene it needs is the sprite drawing's, in port form (OV-69, closed in `44`).

A port with its own colour tables must keep this one byte of state in a place the pause can read.

## 6. What the OS does for the game, and what the port does instead

| The OS does | What it does for the game | The port instead |
|---|---|---|
| the vertical blank (60 / s NTSC, 50 / s PAL) | calls the deferred vector `VVBLKD` = `$A5FD`: the whole game frame; `RTCLOK2` (`$14`) counts the frames before it | a timer that calls `play_frame` once per frame and counts a byte clock |
| shadow to chip copy | the OS copies the colour, display-list, DMA, priority and character-set shadows to the chips in its vertical blank; the game writes only the shadows (and some chip registers directly: `33`) | the renderer reads `w.shadow` / the chip writes of the frame |
| joystick and triggers | the OS reads `PORTA`, `TRIG0`, `TRIG1` every frame into `STICK0-1`, `STRIG0-1` | `Platform.stick(port)`, `Platform.trigger(port)` |
| keyboard | the keyboard interrupt of the OS stores the key code in `CH` and sets `KEYDEL`; the OS counts `KEYDEL` down | `Platform.key()`, `Platform.key_delay()` (only the key loop reads them) |
| console keys | `CONSOL` is read by the game directly | `Platform.console()` |
| attract mode | the OS counts `ATRACT` up; when it passes its limit the OS sets `DRKMSK` / `COLRSH`, which darken and cycle every colour the display-list handlers write; any key or stick input resets the count (the game also writes `ATRACT` itself) | `Platform.attract()`; the game's writes to `ATRACT` (`$4D`) are outputs |
| display-list interrupts | the OS non-maskable interrupt routine jumps through `VDSLST` = `$A573` (game) or `$A5CE` (title) at each interrupt line of the display list | five colour / character-set changes at fixed scan lines (`35`, section 4): the renderer's band table |
| power-on | the OS reads the cartridge header, calls INIT (a bare `RTS`), jumps to RUN with the interrupts as `37` shows; the OS's zeros at `$0400-$041F` and `$0B98-$0BFF` are used | the port starts `Start`'s expansion from its own clean state (`37`, section 5) |

**The timing contract**: one call of `play_frame` per frame, 60 per second on NTSC (on PAL 50 per second: the frame body takes 122 of 312 scan lines there, `38`, OV-62); in the original the frame body takes at most 234 of 262 scan lines (`38`: 28 lines of margin), so a port has no timing to hit but the frame. The five colour interrupts of the game screen and of the title are at fixed lines (`35`, section 4): a renderer applies them per band.

## 8. Limits

- **The closure experiment is a sample**, not a proof: random states of the stage-50 to stage-66 kinds, 1,000 to 1,300 a kind, with the maze pointer, positions and states kept to the game's own (as `42`). The static facts (the 15 read instructions, the 2 control transfers) are proved by the scan of the ROM; the dynamic run adds that the **indirect** reads (`lda (zp),y`, indexed forms) never reach the outside. The pointers the code reads through are in `29`; the run is the check of their reads.
- **`Start` is not in the closure run**: its reads of `POKMSK` and the clock are in wait loops that need a real clock. The start-up is `37` (three machines measured, what the game takes from the power-on state).
- **The key loop's one pass** is compared where it waits for an input; its branches are `40` (every one run in the real game).
- **OV-68: the collision registers** are an input the hardware computes from the pictures of the sprites. The game tests them only as bits (`M1PL`, `M2PL`: Pac-Man's missiles on a ghost's player; `M2PF`: the bonus item). The port needs a geometry for them: **built since this chapter was written** (`50`, `tools/gtia_collisions.py`, checked on 73,111 random scenes and 27,193 frames of real play, 0 differences), and available as `GtiaCollisions` in `tools/platform_iface.py`. The vertical half of the contact test is in the game (`|dy| < 5`, `41`). What the model takes is the scene (positions and pictures of the pages) the original's drawing leaves, which the port produces in `tools/core_draw.py` (OV-69, closed: `44`).
- **The PAL machine** has not been run through this interface test (PAL timing is OV-02's concern, `38`).
