# 37 - Startup (stage 61)

GENERATED by `python -I tools/analyze_startup.py --doc docs/37-startup.md` from the logs of `tools/altirra_startup.cmd` (three machines), `tools/altirra_warmstart.cmd`, the interpreter and `tools/startup_poison.py`; evidence: `analysis/evidence-startup-summary.txt`. Tests: `tests/test_startup.py`.

## 1. The result

- **The cartridge is started exactly as the header says**: the OS reads `$BFFC` (cartridge present) and `$BFFD` (option byte), calls INIT (`$BFFE/F` = `$A6B4`) once and later jumps to RUN (`$BFFA/B` = `$A386`); RUN comes 10 frames after INIT on the NTSC OS-B machine (7 PAL, 2 built-in OS). INIT is **not a routine of its own**: `$A6B4` is the shared `RTS` at the end of `ReadSrcHighNibble` (the label `Init` of the source), so the OS's INIT call does nothing.
- **`Start` needs nothing from the OS but a normal CPU state**: the OS enters RUN with S=`$FF`, interrupts enabled (I=0) and the decimal flag clear (D=0; `Start` has no `CLD` and relies on it), on all three machines. Everything the game owns (`$18-$3F`, `$80-$FF`) is cleared by `Start` itself.
- **In 7 frames (NTSC) `Start` builds all the game's data and installs the vertical-blank handler**: RUN at frame 32, `SETVBV` at frame 39, the end of the copies, and with it the first pass of the key loop, at frame 41, the title menu (`GameState` 3) at frame 286 (the copyright screen runs 246 frames). From RUN to `SETVBV` it takes 6 frames on PAL and 8 with the built-in OS (the OS's own timing and the number of scan lines differ; the code is the same).
- **The state at the first key loop is the same on all three machines**: the tables `$0600-$07FF` equal the interpreter's expansion byte for byte, and the chips hold `DMACTL`=`$3E`, `NMIEN`=`$C0`, `PMBASE`=`$20`, `GRACTL`=3, `IRQEN`=`$C0`, `SKCTL`=7.
- **What the game takes from the power-on state is small and listed** (section 4): the OS's RAM clear (zeros at `$0400-$041F` and `$0B98-$0BFF`) and a few OS zero-page values. With random RAM instead the game starts at the same frame and plays on; the differences are garbage in the unused tails of the maze copies and stray pixel rows in the player-missile pages.
- **A warm start (the RESET key) is a second cold start for the game**: the OS clears `GameState`, calls INIT and RUN again with the same registers; `Start` begins from scratch (section 5).

## 2. From power-on to RUN (the OS side)

| Step (NTSC, OS-B) | Frame | What happens |
|---|---|---|
| reset | 3 | the OS clears its variables; `GameState` (`$19`) is zeroed by the OS at `$F140`: the game's variable lies in the OS's cleared range |
| cartridge check | 3 | the OS reads the header: `$BFFC` at `$F244`, `$BFFC` at `$F247`, `$BFFD` at `$F24C`, `$BFFC` at `$F254`, `$BFFC` at `$F1B3`, `$BFFE` at `$F239`, `$BFFF` at `$F239` |
| INIT | 22 | `JSR` through `$BFFE`; the routine is the `RTS` at `$A6B4` |
| RUN | 32 | the OS jumps through `$BFFA` to `Start` (`$A386`) with S=`$FF`, P=`$31` (I=0, D=0), A=`$04`, X=0, Y=`$80` (built-in OS: P=`$30`, X=Y=1) |

Header (`07`): `$BFFA/B` RUN = `$A386`; `$BFFC` = 0 (cartridge present); `$BFFD` = `$04` (bit 2: run the cartridge; bit 0 clear: no disk boot); `$BFFE/F` INIT = `$A6B4`.

After the copies the key loop (`$A4BA`) runs; the game proper is driven by the vertical-blank handler: `GameState` 1 (written by `Start`) becomes 2 at the first handler run (frame 40, `$A70A`), 3 (the title menu) 246 frames later. A START press then jumps to `$A537`, the single start-game entry (`21`).

`Start` runs once per RUN and never returns (the key loop is the main program); the restart label `$A477` is also the target of every START (`$A541`): it clears `$20-$3F` and copies the maze again but does not repeat the expansion.

## 4. What the game takes from the power-on state

Method (`tools/startup_poison.py`): the 6502 interpreter runs `Start`, then the key loop with the vertical-blank handler and the display-list interrupts entering at random places, a START press at frame 480 and a joystick that changes direction (900 frames), with the whole RAM filled with random bytes (4 fills) and with zeros (what the OS leaves); the OS-owned inputs of `33` (`POKMSK`, `RTCLOK2`, `ATRACT`, `DRKMSK`, `COLRSH`, the stick and trigger shadows, `CH`) and the hardware registers are given. Every read of a byte that nothing has written is recorded.

| Reader | Addresses read before written | What it is | Live check at RUN |
|---|---|---|---|
| `Copy0800To0C00` | `$0B98-$0BFF` | the three maze copies read 1,024 bytes from `$0800`; the maze is 920 bytes, so `$0B98-$0BFF` (104 bytes) of RAM that nothing wrote are copied into the tails of the copies (`$0F98`, `$1398`, `$1798`); never read afterwards | zero on all machines, cold and warm |
| `DliHandler2` | `$005E-$005F` | `DliColors` `$5E/$5F`: the display-list interrupts of the first frame(s) read the band colours before the key loop has stored them (`$A4C3`); the OS leaves `$42 $9C` there | `$42 $9C` on all machines |
| `DrawAllInPlace` | `$0400-$0402` `$040D-$040F` | the 16-byte picture copy reads its source from `$0400-$0402`, `$040D-$040F`: unused RAM that is meant to be blank; the bytes are copied into the player-missile pages | zero on all machines, cold and warm |
| `InitDisplay2` | `$0000-$000F` `$0410-$0411` `$041D-$041F` | the same copy (`InitDisplay2` jumps into the tail of `StepAndDrawEntity`, `29`): `$0410-$0411`, `$041D-$041F` into RAM, and `$0000-$000F` with the destination in ROM (no effect) | `$0400-$043F` zero on all machines |
| `VbiHandler` | `$0045` | `dec $45` (the debounce counter) before the key loop has set it; the key loop sets it to 1 before it is ever tested | `$00` at RUN |

With random RAM the game starts at the same frame (481) and plays on; what it writes that differs from the zero-filled run is only `$0045` (the counter), the tails of the maze copies (`$0F98-$0FFF`, `$1398-$13FF`, `$1798-$17FF`) and 88 bytes of the player-missile pages `$2300-$27FF` (the garbage picture rows above). Nothing in the game's own variables, the maze, the tables or the score depends on the fill. **On a real machine the OS clears RAM at power-on and a warm start leaves these areas as they were (zero: the game never writes them), so the game always sees zeros there.**

## 5. The warm start

- warm start (F5 posted to Altirra's window while the title ran): the OS writes GameState = 0 at $F16E (frame 14258), calls INIT again (frames 22, 14258; return into the OS at $F1BC), and jumps to RUN again at frame 14268 with S=$FF P=$31 A=$04 X=$00 Y=$80 (cold: S=$FF P=$31 A=$04 X=$00 Y=$80)
- zero page at RUN, cold against warm: 2 of 256 bytes differ ($05 $08); the game's own ranges $18-$3F and $80-$FF (which Start clears): the same in both
- $0400-$043F at the warm RUN: all zero
- $0B98-$0BFF at the warm RUN: all zero

## 6. Limits

- The live runs are Altirra 4.40 (OS-B NTSC and PAL, the built-in OS); a real machine's power-on RAM and the timing of its OS are not tested (owner's decision, `OPEN-VERIFICATION.md` OV-01).
- The fill experiment runs in the interpreter with a fixed schedule of interrupts and inputs: it shows every read of an unwritten byte on that schedule, not on every possible one (the abstract search of `34` covers the state variables, not these RAM areas).
- The values read from hardware registers and the OS-owned inputs are taken as given (they are the inputs of `33`).
