# 28 - The Stack (stage 44)

GENERATED by `python -I tools/analyze_stack.py --write docs/28-stack.md` from the trace of `src/asm/pacman.s`, the routines of `23-function-table.md`, and `analysis/evidence-stack-summary.txt` (the emulator measurement). Tests: `tests/test_stack.py`.

## 1. The result

- The program uses **the hardware stack only** (page 1, `$0100-$01FF`): no instruction of the ROM addresses that page (0 found), there is no heap, no software stack and no stack frame, and the stack is **not game state**: no game variable, table or buffer lives in it.
- The stack pointer is set once, to **$FF** (the whole page, 256 bytes), by the `TXS` at `$A480`: the instructions before it count X down from $1F to $FF (`dex / bpl`), so X is $FF at the `TXS`.
- The only stack operations are: `JSR` / `RTS` (124 call sites, 2 bytes each), the interrupt entry and `RTI` (3 bytes), and the 8 pushes (each with its pop) listed in section 2. **Every routine is balanced**: on every path to every `RTS` / `RTI` it has popped what it pushed (81 routines checked, 0 unbalanced), and at every join of two paths the own depth is the same (0 mismatches).
- There is no indirect jump and no `PHA / PHA / RTS` jump trick, so no pushed value is ever used as an address except by `RTS` / `RTI`: **the call structure of `23-function-table.md` is the whole control flow** and a C function call per `JSR` reproduces it exactly.

Entry points: **Start 6**, **VbiHandler 10** (the whole game frame runs from the vertical-blank interrupt: `FrameDispatch` is entered by it), **DliHandler1 2**, **DliHandler2 3** bytes beyond what the hardware and OS have pushed.

Contexts that can be stacked: the main program (`Start`), an NMI that runs the vertical-blank handler (the game frame), and - because a display-list interrupt is also an NMI and the frame code runs on into the display - one display-list interrupt inside it. Two facts from the code limit this:

- **Only one display-list handler is active at a time.** `SetDisplayList` writes the display list and `VDSLST` together: the game screen sets `DliHandler1` (the call at `$A49B`, `ldy #$73`), the title and attract screens set `DliHandler2` (`InitDisplay2`, the call at `$A621`, `ldy #$CE`). The deepest chain below runs only on the game screen (`TurnControl` handles a turn switch in a two-player game), so it can be interrupted by `DliHandler1` only; `DliHandler2` can only interrupt the title-screen frames, whose chains are shallow.
- **The interrupts do not nest inside each other's handlers**, and the OS pushes nothing before a display-list interrupt (it jumps through `VDSLST`) but 3 bytes (A, X, Y) before the deferred VBI handler; the hardware pushes 3 bytes for each. Both are measured (section 4: the interrupted pc is read from the stack at every entry).

So the bound **by construction**, for every combination whether it occurs or not, is `Start 6 + VBI entry 6 (3 hardware + 3 OS) + VbiHandler 10 + DLI hardware 3 + the larger DLI handler 3` = **28 bytes** of the 256. The case that really occurs (the deepest chain interrupted by `DliHandler1`, with the main program idle) is `6 + 10 + 3 + 2` = **21 bytes**; section 4 shows that the measurement gives exactly that.

## 5. What the port does with this

- The C code uses the C call stack: one function call per `JSR`, one `return` per `RTS`; nothing to emulate. The stack page is not part of the state the equivalence tests (stages 86-87) compare, except as a bound: the original never uses more than the depth in section 4 (of 256 bytes).
- The interrupt handlers become functions that the hardware layer calls at the right moments of the frame (stage 79/80); `PHA` / `PLA` / `PHP` / `PLP` become locals (`27-local-variables.md`).
- Nothing in the ROM depends on the stack contents surviving a call except through `RTS` / `RTI`; there is no `longjmp`-like use. The restart at `$A477` (`TXS`) resets the stack pointer: in C it is a jump back to the start of the main loop.
