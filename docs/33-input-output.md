# 33 - Input and Output Observation (stage 57)

GENERATED by `python -I tools/analyze_io.py --doc docs/33-input-output.md` from the traced code of `src/asm/pacman.s`, the curated meaning of each register (`PURPOSE` in the tool) and `analysis/evidence-io-summary.txt` (`tools/run_io_audit.ps1`). Tests: `tests/test_io.py`.

## 1. The result

- The cartridge code touches the outside world at **133 instructions** in **51 registers or register groups**: 6 ANTIC, 13 GTIA, 15 OS page 2, 5 OS zero page, 12 POKEY. No other address of the hardware pages or of the OS pages is addressed by any data instruction (the 31 indirect `(zp),y` instructions reach RAM and ROM data, never a register: `29-pointers.md`), and the PIA (`$D300`) is not touched at all: the joystick comes in through the OS shadows (`STICK0`, `STRIG0/1`) that the OS fills in its vertical blank.
- **Inputs** (what the game reads, the only ways a player or the machine can influence it): the joystick directions (`STICK0,x`, x = the player on turn), the triggers (`STRIG0`, `STRIG1`), the three console keys (`CONSOL`), the keyboard (`CH`, `KEYDEL`: the space bar only), the polynomial random counter (`RANDOM`, 3 places), the collision registers (`M2PF`, `M1PL`, `M2PL`), the OS clock (`RTCLOK2`) and the two OS attract-mode variables (`DRKMSK`, `COLRSH`).
- **Outputs**: the display (ANTIC pointers, the character-set page, `WSYNC`, `NMIEN`, `PMBASE`, the GTIA positions and colours and their OS shadows), the sound (POKEY `AUDF1-4`, `AUDC1-4`, `AUDCTL`) and the hand-over to the OS (`VDSLST`, `SDLSTL/H`, `SDMCTL`, `GPRIOR`, `ATRACT`, `POKMSK`, `IRQEN`, `SKCTL`).
- **Observed live**: eleven sessions of the real game (fullgame, pregame, gameover, p2win, levels, pause, frightened_cases, house_frightened, catch, and the two input exercisers `inputs` and `inputs1`) executed **every one of the 133 instructions**; at each execution the effective address and the value were printed. Section 4 lists, per register, the number of accesses and the values seen.
- This replaces the heuristic scan of `06-hardware-and-memory-map.md` (absolute addresses only, written from memory): **the list below is complete, including the indexed forms**, and every register has the meaning the game gives it.

## 2. How it was found and observed

1. **Static**: every instruction of the traced ROM code (2,925, `26-control-flow-graphs.md`) whose operand lies in `$D000-$D7FF`, `$0200-$02FF` or is one of the five OS zero-page variables the game shares with the OS (`POKMSK $10`, `RTCLOK2 $14`, `ATRACT $4D`, `DRKMSK $4E`, `COLRSH $4F`), in absolute, zero-page or indexed form; the direction is read from the mnemonic (`sta/stx/sty` write; `lda/cmp/ora/bit` read). No instruction addresses the PIA or any other chip; the OS ROM is entered at two places only: `jsr SETVBV` (`$A460`, in `Start`: the deferred vertical-blank vector) and `jmp XITVBV` (`$A60D`, the end of the vertical-blank handler).
2. **Live**: `tools/run_io_audit.ps1` copies a session harness, appends one tracepoint per instruction (`bt <pc> "IO <pc> a=<effective address> v=<value>"`: the register A, X or Y for a store, the memory byte for a read) and runs it in Altirra 4.40 (NTSC, OS-B, `Altirra_fast.ini`); nothing is written to the emulated machine by the tracing. The harnesses' own test aids are those of `04-analysis-tools.md` (the injected STICK0 / CONSOL / STRIG values are the inputs under observation).
3. **Compare**: `tools/analyze_io.py` aggregates the logs per instruction and per register.

## 5. Reading the values

- **Inputs**, values seen: `STICK0` (`$0278`, player 1) and `STICK1` (`$0279`, read for player 2's turn) show `$0F` (nothing), the four directions `$0E` up, `$0D` down, `$0B` left, `$07` right and the diagonals `$0A`, `$06` (the game refuses two direction bits at once, `20-pacman-and-death.md`); `STRIG0` and `STRIG1` show `1` (not pressed) and `0` (pressed): the trigger starts a game at the title and in the countdown (`21-start-gameover-title.md`); `CONSOL` shows all eight values `$00-$07` (`$07` nothing, `$06` START, `$05` SELECT, `$03` OPTION, `$04` SELECT + START, `$02` OPTION + START, `$01` OPTION + SELECT, `$00` all three: the game acts on the first three alone and ignores the others); `CH` shows `$FF` and `$21` (the space bar, the pause key); `KEYDEL` is 0 whenever it is read; `RANDOM` returns every value; the collision registers show the contact and bonus bits.
- **Outputs**: the values written to the POKEY and GTIA registers are those of the sound and colour chapters (`22-sound.md`, `15-small-tables.md`, `16-ghost-frames.md`); the one-time writes of `Start` (`SDMCTL $3E`, `GRACTL $03`, `PMBASE $20`, `NMIEN $C0`, `SKCTL $07`, `IRQEN` = `$C0`: the break key and keyboard interrupts) are each seen once per run (11 runs, 11 accesses: the restart of a game at `$A477` does not repeat them).
- The input values were **injected** in these sessions (STICK0 by the bots, CONSOL / STRIG at the controller reads, CH for the pause key, `04-analysis-tools.md`): what the audit observes is what the game *reads*; a real person produces the same values through the OS (OV-23: a real keyboard event was run once and acted on, the same value reached `CH`).

## 6. Limits

- The meaning of each register is the game's use of it, written from the code and the live values; the hardware meaning of the bits (for example `CONSOL` bit order, `M1PL` bits) is the one Altirra implements and the game's behaviour confirms, but it has not been cross-checked against a printed hardware manual (the open item 1 of `06-hardware-and-memory-map.md`).
- Only the cartridge code is traced: the OS routines that copy the shadows to the hardware (`STICK0` from the PIA, `PCOLR0` to `COLPM0`, `SDLSTL` to `DLISTL`, the clock) run in the OS ROM and are not part of this chapter.
- Real hardware and the keyboard hardware path are outside the emulated sessions (OV-01, OV-23).
